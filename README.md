# Kodifly DWG and DXF viewer

A standalone website that opens DWG and DXF drawings in the browser. The file is read and drawn
on the visitor's own device and is never uploaded. The site exists to generate leads for Kodifly.

## Run it

```bash
pnpm install
pnpm dev        # http://localhost:8020
pnpm test       # unit tests
pnpm e2e        # Playwright end-to-end tests (uses your installed Chrome)
pnpm typecheck
pnpm knip       # unused files, exports and dependencies
pnpm build
```

`pnpm dev` and `pnpm build` first copy the DWG engine (`libredwg-web.wasm`) into `public/wasm/`.

## How it works

```
file ──> Web Worker (src/convert/worker.ts)
           1. sniff the format from the first bytes
           2. DWG: LibreDWG (WebAssembly, loaded on demand)
              DXF: dxf.ts (plain TypeScript, read in chunks)
           3. extract.ts flattens blocks, curves and text
         ──> CadDrawing JSON ──> canvas viewer (src/cad)
```

- `src/convert/` is a TypeScript port of `cad_floor_plan/extract.py` from `ss-ifc-to-3d-tiles`.
  It produces the same `CadDrawing` JSON the platform's backend produces (`src/cad/types.ts`).
- `src/cad/` is the CAD floor-plan viewer copied from
  `kodifly-platform/packages/viewer-app/src/features/cad-floor-plan`. `platform.tsx` stands in
  for the platform packages it imported, and `chrome.css` holds the toolbar styles.
- `src/site/` is the landing page, viewer screen, lead form and export.
- `src/app/api/lead/route.ts` is the only endpoint that receives user data. It never receive
  drawings. Set `LEAD_WEBHOOK_URL` (see `.env.example`) to deliver leads; without it they are
  only logged by the server.

Both parsers hand `extract.ts` the same shape (`src/convert/source.ts`). To swap the DWG engine,
return that shape from another parser in `worker.ts`; nothing else changes.

## Supported

- DWG from AutoCAD R13 to 2018+, and text (ASCII) DXF. Model space and paper-space layouts.
- Lines, polylines (with bulges), arcs, circles, ellipses, splines, solid and pattern hatches
  (pattern hatches as outlines), text, MTEXT, attributes, dimensions, leaders and nested blocks.

## Viewer features

- Pan, wheel and pinch zoom, fit; select by object, layer or block; properties; layers; search.
- Measure distance, area and angle, snapping to nearby vertices.
- Model and layout tabs; several drawings open at once; zip archives are unpacked in the browser.
- Export: PNG (current view), SVG and PDF (whole sheet). The PDF is written by
  `src/site/exportDrawing.ts` with no library; its text uses Helvetica, so only Latin-1 prints.
- Command palette with every action and its shortcut: Cmd/Ctrl+K or `?`.

## Pages and SEO

- `/` plus three search landing pages (`/dwg-viewer`, `/dxf-viewer`, `/open-dwg-without-autocad`).
  They are the same viewer under a different heading; their copy lives in `src/site/content.ts`.
- `/privacy` and `/terms`. The wording is a plain-language draft and has not had a legal review.
- `sitemap.xml`, `robots.txt`, a social preview image and JSON-LD are generated by `src/app`.
- Set `NEXT_PUBLIC_SITE_URL` before deploying, or canonical links and the sitemap point at
  localhost. Set `NEXT_PUBLIC_PLAUSIBLE_DOMAIN` to load Plausible analytics.
- `NEXT_PUBLIC_POSTHOG_KEY` and `NEXT_PUBLIC_POSTHOG_HOST`: PostHog project key (public, `phc_…`) and region.
  Events are proxied through `/ingest` on the site's own origin so blockers do not drop them. Autocapture and
  session recording are off on purpose: a visitor's drawing must never appear in a replay. Events sent:
  `$pageview`, `file_opened` (format, size), `file_too_large`, `parse_failed`, `sample_opened`, `export_clicked`,
  `trial_clicked` (where: header, viewer, palette, too_heavy, footer_cta).

## Known limits

- Binary DXF, password-protected drawings, 3D solids, images, xrefs, tables and multileaders are
  not drawn. Unsupported object counts show in the status chip.
- Layout tabs draw the model through each rectangular plan-view viewport. Viewports with a 3D
  view or a non-rectangular outline, and per-viewport frozen layers, are not handled.
- Layers that use a true colour in a DWG fall back to their nearest indexed colour.
- Text is drawn with a browser font, not the drawing's SHX/TTF fonts. GBK, Big5, Latin-1 and
  `\U+XXXX` text decode correctly (`tests/encoding.test.ts`).
- The DWG and phone size limits in `useDrawingFile.ts` are still estimates (see Benchmarks).

## Benchmarks

Measured on one desktop (Chrome, production build) with `BENCH_DIR=<folder> pnpm e2e bench
--project=desktop`. The DXF files are synthetic (lines, circles and text on one layer).

| File | Objects | Time to first render | Page memory | Pan frame (median) |
| --- | --- | --- | --- | --- |
| Real DWG, 1.7 MB | 22,847 | 1.9 s | 37 MB | 13 ms |
| DXF, 1 MB | 25,000 | 0.9 s | 28 MB | 14 ms |
| DXF, 10 MB | 240,000 | 1.4 s | 76 MB | 15 ms |
| DXF, 50 MB | 1.2 million | 6.0 s | 329 MB | 13 ms |
| DXF, 100 MB | 2.1 million | 10.8 s | 585 MB | 12 ms |

Page memory excludes the worker that parses the file. Not measured: DWG files above 1.7 MB,
text-heavy, hatch-heavy and geo-referenced drawings, Safari, and real phones. `BENCH_MB=1,10
pnpm vitest run tests/bench.test.ts` times the parser alone.

Lighthouse (mobile emulation, production build on localhost): performance 100, accessibility
100, best practices 100, SEO 100; LCP 0.9 s, CLS 0.

## Offline

`public/sw.js` caches the DWG engine, the app code and the samples, so after one visit the viewer
works without a connection. It is registered in production builds only.
